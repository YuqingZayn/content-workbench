# 图片预览优化（0.1.1）

原来的素材卡片、内容封面、关联素材选择器直接加载原图，而且每次打开项目都会重新读取已登记媒体并计算哈希。PNG 的文件大小并不能代表解码成本：例如 13108 × 32768 的 RGBA 图像，完整像素缓冲约为 1.6 GiB。

## GitHub 参考与采用方式

- [Sharp](https://github.com/lovell/sharp)：采用其 libvips 图片处理能力，通过顺序读取、缩小尺寸和 WebP 输出生成预览。实际使用版本为 0.35.4，Apache-2.0。
- [Immich 的媒体服务](https://github.com/immich-app/immich/blob/main/server/src/services/media.service.ts) 与 [媒体处理实现](https://github.com/immich-app/immich/blob/main/server/src/repositories/media.repository.ts)：参考缩略图、详情预览、原图分开，以及后台任务生成预览的组织方式。本工程独立实现桌面缓存和队列，没有复制其 AGPL 代码，也不引入其服务器组件。

## 本次实现

- 素材卡片、内容列表、文案预览及素材选择器使用最长边 512 px 的 WebP。
- 图片详情默认使用最长边 1600 px 的快速预览，用户点击“查看原图”后才加载原始图片。
- 两个后台 Worker 处理缩图，每个 Worker 的 libvips 并行度为 1；处理不占用 Electron 主线程。使用顺序读取支持超大 PNG，限制输入像素上限，并设置处理超时。
- 缓存保存在应用用户目录的 `cache/previews-v1`，不修改源图片、不进入业务项目和发布包。缓存键包含源路径、登记哈希、文件大小、修改时间和预览尺寸，重复请求合并，重启后继续复用。
- 缓存响应带 ETag，经过素材归属和源文件检查后可返回 304。源文件缺失或变化时不返回失效预览。
- 页面使用懒加载、异步解码和固定预览占位；离开页面后尚未开始的无效请求可跳过。解码失败显示占位，详情仍可选择原图。
- 重新打开项目时，已登记且路径、大小、修改时间未变化的素材跳过重复读文件及哈希。新文件和变化文件仍按原有导入流程处理，发布快照仍验证内容哈希。
- 内容库的布局和多平台组织方式保持原样。

## 验证

以下是本机一次测试的观测值，不作为其他硬件的时间保证：

| 自生成测试图片 | 结果 |
|---|---|
| 8 张 3200 × 2400 PNG，总大小 | 246,171,912 字节 |
| 8 张卡片缩略图总大小 | 16,788 字节 |
| 原图加载并解码 | 约 1,103 ms |
| 第一次进入并生成缩略图 | 约 892 ms |
| 缓存后再次进入素材库 | 约 64 ms |

另以本地实际超大图验证了 13108 × 32768 PNG 的顺序缩小读取。业务素材和截图不提交公开仓库。

自动化覆盖：缓存合并与重启复用、透明度、原图不变、源文件变化、损坏图片和取消请求、未授权素材、ETag、详情与原图切换、桌面原有闭环。Windows 打包启动检查还会实际生成一张缩略图，验证 Worker、Sharp 原生模块和动态库都进入安装包。

```powershell
npm run test:media
npm run test:e2e
npm run dist:win
npm run test:package
```

本次没有实现视频转码或内容文件夹布局。超大图片首次生成预览仍需处理时间；后续浏览使用缓存。
